# P01-S02 — .NET 10 Project Structure, Build Conventions & Central Package Management

## هدف جلسه

در این جلسه ساختار پایه‌ی `CleanCommerce` را از یک مجموعه Project ساده به یک Repository با قواعد Build و Package Management متمرکز تبدیل کردیم.

هدف اصلی این بود که قبل از ورود به پیاده‌سازی قابلیت‌های واقعی سیستم، قراردادهای فنی Repository مشخص باشند؛ به‌طوری‌که Projectهای مختلف تنظیمات مشترک را تکرار نکنند و جهت Dependencyها نیز با معماری موردنظر پروژه سازگار باشد.

---

## 1. ساختار Solution

در پایان جلسه Solution شامل پنج Project اصلی است:

```text
CleanCommerce
├── src
│   ├── CleanCommerce.Api
│   ├── CleanCommerce.Application
│   ├── CleanCommerce.Domain
│   ├── CleanCommerce.Infrastructure
│   └── CleanCommerce.Playground
└── tests
```

پوشه‌ی `tests` در حال حاضر یک Solution Folder خالی است و در جلسات آینده میزبان Projectهای تست خواهد شد.

### نقش Projectها

`CleanCommerce.Domain` هسته‌ی مدل دامنه است و نباید برای کار خود به لایه‌های بیرونی وابسته باشد.

`CleanCommerce.Application` محل Use Caseها و منطق Application است و می‌تواند به `Domain` وابسته باشد.

`CleanCommerce.Infrastructure` جزئیات فنی و پیاده‌سازی وابستگی‌های بیرونی را نگه می‌دارد و در ساختار فعلی به `Application` وابسته است.

`CleanCommerce.Api` نقطه‌ی ورود برنامه و Composition Root است. این Project برای راه‌اندازی Application و Infrastructure به هر دو Project مربوطه Reference دارد.

`CleanCommerce.Playground` محیط آزمایشی و آموزشی دوره است و فعلاً وارد Dependency Graph معماری اصلی نشده است.

## 2. چرا تنظیمات مشترک را از csprojها خارج کردیم؟

در ابتدا تنظیماتی مانند موارد زیر در Projectهای مختلف تکرار می‌شدند:

```xml
<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
  <ImplicitUsings>enable</ImplicitUsings>
  <Nullable>enable</Nullable>
</PropertyGroup>
```

این روش در یک Solution کوچک قابل مدیریت است، اما با افزایش تعداد Projectها مشکلاتی ایجاد می‌کند:

- امکان متفاوت‌شدن ناخواسته‌ی تنظیمات Projectها
- تکرار Configuration
- دشوارشدن تغییر یک Policy سراسری
- افزایش Diffهای غیرضروری

برای حل این مسئله از قابلیت‌های MSBuild استفاده کردیم.

---

## 3. Directory.Build.props

در Root Repository فایل زیر ایجاد شد:

```text
Directory.Build.props
```

محتوای نهایی آن:

```xml
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
    <WarningsAsErrors>$(WarningsAsErrors);nullable</WarningsAsErrors>
  </PropertyGroup>
</Project>
```

### رفتار MSBuild

هنگام Build یک Project، MSBuild در مسیر والد Project به دنبال `Directory.Build.props` می‌گردد و Propertyهای آن را وارد فرآیند Build می‌کند.

بنابراین لازم نیست هر Project دوباره بنویسد:

```xml
<TargetFramework>net10.0</TargetFramework>
```

Projectهای Repository این مقدار را از Configuration مرکزی دریافت می‌کنند.

### Nullable

با این تنظیم:

```xml
<Nullable>enable</Nullable>
```

Nullable Reference Types برای Projectها فعال است.

همچنین:

```xml
<WarningsAsErrors>$(WarningsAsErrors);nullable</WarningsAsErrors>
```

باعث می‌شود Warningهای مربوط به Nullable به Error تبدیل شوند.

نکته‌ی مهم این Syntax آن است که مقدار قبلی `WarningsAsErrors` را حفظ می‌کنیم:

```text
$(WarningsAsErrors)
```

و Policy مربوط به `nullable` را به آن اضافه می‌کنیم.

## 4. Central Package Management

برای مدیریت متمرکز Version پکیج‌های NuGet فایل زیر را در Root Repository ایجاد کردیم:

```text
Directory.Packages.props
```

محتوای فعلی:

```xml
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>

  <ItemGroup>
    <PackageVersion Include="Microsoft.AspNetCore.OpenApi" Version="10.0.11" />
  </ItemGroup>
</Project>
```

فعال‌سازی:

```xml
<ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
```

به NuGet اعلام می‌کند که Version پکیج‌ها به‌صورت مرکزی مدیریت می‌شود.

در نتیجه فایل `CleanCommerce.Api.csproj` فقط Package را Reference می‌کند:

```xml
<PackageReference Include="Microsoft.AspNetCore.OpenApi" />
```

و Version در `Directory.Packages.props` قرار دارد.

### چرا CPM مهم است؟

فرض کنید در آینده ده Project از یک Package مشترک استفاده کنند. بدون Central Package Management ممکن است Version در ده فایل جداگانه تعریف شود.

با CPM، Reference و Version دو مسئولیت جدا هستند:

```text
Project
   │
   └── PackageReference
             │
             ▼
Directory.Packages.props
             │
             └── Version
```

بنابراین ارتقای Version یک Package مشترک از یک نقطه کنترل می‌شود.

## 5. ProjectReference و Dependency Direction

Dependencyهای ایجادشده در این جلسه عبارت‌اند از:

```text
Application ──→ Domain

Infrastructure ──→ Application

Api ──→ Application
Api ──→ Infrastructure
```

در نتیجه می‌توان ساختار مفهومی را این‌گونه دید:

```text
Domain
  ↑
Application
  ↑
Infrastructure

Api ──→ Application
Api ──→ Infrastructure
```

فلش در این نمودار نشان‌دهنده‌ی Dependency/Reference است.

### Domain

فایل `CleanCommerce.Domain.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk">
</Project>
```

`Domain` به هیچ Project دیگری Reference ندارد.

این ویژگی مهمی است، زیرا هسته‌ی Domain نباید برای تعریف Business Model خود به API یا Infrastructure وابسته باشد.

### Application

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <ItemGroup>
    <ProjectReference Include="..\CleanCommerce.Domain\CleanCommerce.Domain.csproj" />
  </ItemGroup>

</Project>
```

`Application` می‌تواند از مفاهیم Domain استفاده کند.

### Infrastructure

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <ItemGroup>
    <ProjectReference Include="..\CleanCommerce.Application\CleanCommerce.Application.csproj" />
  </ItemGroup>

</Project>
```

در این مرحله فقط Dependency موردنیاز اضافه شد.

یک اصل مهم:

> ProjectReference را صرفاً به این دلیل که «ممکن است بعداً لازم شود» اضافه نمی‌کنیم.

هر Dependency باید دلیل واقعی داشته باشد.

### Api

ساختار فعلی `CleanCommerce.Api.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk.Web">

  <ItemGroup>
    <PackageReference Include="Microsoft.AspNetCore.OpenApi" />
  </ItemGroup>

  <ItemGroup>
    <ProjectReference Include="..\CleanCommerce.Application\CleanCommerce.Application.csproj" />
    <ProjectReference Include="..\CleanCommerce.Infrastructure\CleanCommerce.Infrastructure.csproj" />
  </ItemGroup>

</Project>
```

`Api` به `Application` و `Infrastructure` دسترسی دارد.

## 6. Composition Root

یکی از دلایل دسترسی `Api` به `Infrastructure` مفهوم Composition Root است.

Composition Root جایی است که Object Graph برنامه ساخته و Dependencyها به یکدیگر متصل می‌شوند.

در یک ASP.NET Core Application معمولاً Startup/Bootstrap برنامه در Presentation Host انجام می‌شود.

به‌صورت مفهومی:

```text
Api
 │
 ├── Application abstractions/use cases
 │
 └── Infrastructure implementations
```

در جلسات آینده و هنگام ورود به Dependency Injection این مفهوم را به‌صورت عملی توسعه خواهیم داد.

---

## 7. Dependency Inversion

Clean Architecture به این معنا نیست که هیچ لایه‌ای به لایه‌ی دیگری وابسته نباشد. مسئله‌ی اصلی، جهت Dependencyها و محل قرارگیری Abstractionها است.

به‌طور مفهومی اگر Application به یک قابلیت بیرونی نیاز داشته باشد، می‌توان Contract را در لایه‌ی داخلی تعریف کرد و Implementation را در Infrastructure قرار داد.

مثال مفهومی:

```text
Application
    │
    └── IEmailSender
             ▲
             │ implements
             │
Infrastructure
    └── SmtpEmailSender
```

به این ترتیب Business/Application Logic مستقیماً به جزئیات SMTP وابسته نمی‌شود.

این موضوع در جلسات بعدی هنگام پیاده‌سازی Use Caseها و Infrastructure به شکل کامل‌تری بررسی خواهد شد.

## 8. editorconfig

در طول بررسی Git متوجه شدیم بعضی فایل‌ها Encoding متفاوتی دارند. برای تعریف Convention از این نقطه به بعد فایل زیر ایجاد شد:

```text
.editorconfig
```

محتوا:

```ini
root = true

[*]
charset = utf-8
end_of_line = crlf
insert_final_newline = true
```

### charset

```ini
charset = utf-8
```

Encoding استاندارد فایل‌های متنی Repository را مشخص می‌کند.

### end_of_line

```ini
end_of_line = crlf
```

Line Ending استاندارد Repository را برای محیط Windows روی CRLF قرار می‌دهد.

### insert_final_newline

```ini
insert_final_newline = true
```

مشخص می‌کند فایل متنی با newline خاتمه پیدا کند.

### نکته درباره‌ی فایل‌های قدیمی

اضافه‌کردن `.editorconfig` به این معنا نیست که تمام فایل‌های موجود فوراً Re-encode می‌شوند.

در این جلسه عمداً تمام فایل‌های Repository را به‌صورت دسته‌جمعی Convert نکردیم، زیرا چنین کاری می‌توانست Diffهای غیرمرتبط زیادی تولید کند.

## 9. وضعیت نهایی Projectها

ساختار Configuration اکنون دو سطح دارد:

```text
Repository-level configuration
│
├── global.json
├── Directory.Build.props
├── Directory.Packages.props
└── .editorconfig

Project-level configuration
│
├── CleanCommerce.Api.csproj
├── CleanCommerce.Application.csproj
├── CleanCommerce.Domain.csproj
├── CleanCommerce.Infrastructure.csproj
└── CleanCommerce.Playground.csproj
```

هدف این است که Policyهای مشترک در سطح Repository قرار بگیرند و فایل Project فقط اطلاعات مخصوص همان Project را نگه دارد.

## 10. Build → Inspect → Explain

### Build

پس از اعمال Configurationها و ProjectReferenceها، Solution را Rebuild کردیم.

نتیجه:

```text
5 succeeded
0 failed
0 skipped
```

### Inspect

موارد زیر بررسی شدند:

- پنج Project با `net10.0` Build می‌شوند.
- تنظیمات مشترک از فایل‌های Project حذف شده‌اند.
- `Directory.Build.props` تنظیمات Build مشترک را فراهم می‌کند.
- Version پکیج OpenAPI در `Directory.Packages.props` قرار دارد.
- `PackageReference` داخل API فاقد Version محلی است.
- ProjectReferenceها مطابق Dependency Direction موردنظر ایجاد شده‌اند.
- `Domain` فاقد ProjectReference به لایه‌های بیرونی است.
- Working Tree قبل از Commit بررسی شد.

### Explain

این ساختار باعث می‌شود Repository با رشد Solution قابل‌کنترل‌تر بماند.

به‌جای اینکه هر Project مجموعه‌ای از Policyهای Build و Package Versionهای مستقل داشته باشد، بخش مهمی از Configuration در Root Repository متمرکز شده است.

در عین حال Dependencyهای Projectها Explicit باقی می‌مانند؛ یعنی با مشاهده‌ی هر `.csproj` می‌توان Dependencyهای معماری آن Project را تشخیص داد.

## 11. Git Workflow جلسه

Branch این Session:

```text
session/P01-S02-dotnet10-project-structure-build-conventions-central-package-management
```

Commit اصلی جلسه:

```text
P01-S02: configure project structure and central build conventions
```

Annotated Tag:

```text
P01-S02
```

پس از Build و بررسی نهایی، Branch جلسه Push و سپس تغییرات آن وارد `Develop` شد.

قاعده‌ی دوره از اینجا به بعد:

```text
Develop
   │
   ├── create session branch
   │
   ├── implement + learn
   │
   ├── build + inspect
   │
   ├── commit + push
   │
   ├── tag session
   │
   └── merge back to Develop
            │
            └── next session branch
```

بنابراین Branch هر Session جدید از آخرین نسخه‌ی معتبر `Develop` ساخته می‌شود.

## 12. نکات کلیدی جلسه

- تنظیمات مشترک Build نباید بی‌دلیل در تمام `.csproj`ها تکرار شوند.
- `Directory.Build.props` برای تعریف Propertyهای مشترک MSBuild در سطح Repository استفاده می‌شود.
- Central Package Management، Version پکیج‌ها را از Projectهای مصرف‌کننده جدا می‌کند.
- `PackageReference` مشخص می‌کند Project چه Packageای می‌خواهد؛ `PackageVersion` Version مرکزی آن را تعیین می‌کند.
- Dependencyهای Project باید آگاهانه و فقط در صورت نیاز ایجاد شوند.
- `Domain` باید تا حد ممکن مستقل از جزئیات بیرونی باقی بماند.
- `Api` نقش Host و Composition Root برنامه را بر عهده خواهد داشت.
- `.editorconfig` قراردادهای فایل‌های متنی Repository را مشخص می‌کند.
- موفقیت Build به‌تنهایی کافی نیست؛ باید خروجی و Dependencyها نیز Inspect و Explain شوند.
